# Creating static ASCII art for a monospace web page (hand-made and code-generated)

Scope: techniques, algorithms, tools and conventions for drawing a large ASCII envelope / love letter with a heart seal, a huge "Will you open ?" headline and ASCII-bordered buttons, all as monospace text on a Python-generated web page. Research date: 2026-10-31. All snippets below are original (drawn or generated by the researcher in this session) unless attributed.

---

## 1. Hand-drawn line-art conventions; 7-bit ASCII vs Unicode box-drawing / block / braille

### Takeaway
Classic line art uses a small set of 7-bit characters (``/ \ | _ - ( ) < > = . , ' ` ``) to imitate outlines and density characters (`$ #`) for shading. It needs a monospaced font. Unicode box-drawing (U+2500–U+257F) and block elements (U+2580–U+259F) give cleaner joins and solid fills, but they depend on the font and browser rendering, and the newer "legacy computing" blocks (sextants and similar) have poor font support. For a love-letter page that should look like "real ASCII art", pure 7-bit is the safest base. Use box-drawing or blocks only for deliberate accents such as rounded button borders or a solid headline, with a monospace font stack known to contain them.

### Cited Findings
- ASCII art is built from the 95 printable characters of the 1963 ASCII standard, plus proprietary extended sets. The term is also used loosely for any text-based art. — [Wikipedia: ASCII art](https://en.wikipedia.org/wiki/ASCII_art)
- Line art imitates outlines with `/ \ | _ - ( ) < > =` and similar symbols. Shading uses characters of different visual density such as `$#`. — [Wikipedia: ASCII art](https://en.wikipedia.org/wiki/ASCII_art)
- "Oldskool" (Amiga-scene, from about 1992) style mostly uses `_/\-+=.()<>:` for an outlined look. "Newskool" uses strings like `$#Xxo` and tonal characters. — [Wikipedia: ASCII art](https://en.wikipedia.org/wiki/ASCII_art)
- Block/ANSI/"high ASCII" art uses IBM code page 437 extended characters (1979, PC DOS/MS-DOS) for box-drawing and block characters. Braille and block-element art makes pixel-like images from characters such as `░ █ ▄ ▀` and braille `⣿ ⣴`. — [Wikipedia: ASCII art](https://en.wikipedia.org/wiki/ASCII_art)
- Most ASCII art needs a monospaced font (Courier, Consolas and the like) so that columns line up. Proportional fonts (Helvetica, Times) distort or ruin it. Unicode offers many more characters, but a fixed-width font that covers a large subset is hard to find. — [Wikipedia: ASCII art](https://en.wikipedia.org/wiki/ASCII_art)
- Code point ranges:
  - Box Drawing is U+2500–U+257F (128 characters).
  - Block Elements is U+2580–U+259F (32 characters, including the shades `░▒▓`).
  - Double-line characters sit in U+2550–U+256C.
  - Rounded corners `╭ ╮ ╯ ╰` are U+256D–U+2570.
  - Dashed variants are U+2504–U+250B and U+254C–U+254F.
  - Light (U+2500 `─`, U+2502 `│`) and heavy (U+2501 `━`, U+2503 `┃`) weights are separate characters.
  — [Wikipedia: Box-drawing characters](https://en.wikipedia.org/wiki/Box-drawing_characters)
- Box-drawing characters are designed to connect with their neighbours, so they generally work only in monospaced fonts. Many fonts include only the subset from the IBM PC set (WGL4). — [Wikipedia: Box-drawing characters](https://en.wikipedia.org/wiki/Box-drawing_characters)
- "Symbols for Legacy Computing" (U+1FB00 onward, Unicode 13.0) includes Teletext 2×3 "sextant" pixel characters (64 combinations). A Supplement block (U+1CC00 onward) arrived in Unicode 16.0 (September 2024). Font support is poor: Noto Sans Symbols 2 covers it only partially, and missing glyphs show as boxes or question marks. — [Wikipedia: Box-drawing characters](https://en.wikipedia.org/wiki/Box-drawing_characters)

### Inferences
- **Glyph roles inside a cell.** These follow from standard monospace glyph design and were not taken from a cited source.

  | Glyph | Role |
  |---|---|
  | `_` | Sits at the bottom of the cell, so a "top edge" drawn with `_` belongs on the row *above* the shape. This is why envelopes and boxes start with a row of underscores. |
  | `-` | Mid-height horizontal |
  | `‾` | Not ASCII, so avoid it |
  | `\|` | Full-height vertical |
  | `/` `\` | Diagonals |
  | `( )` | Gently curved verticals |
  | `.` `,` | Low rounding / bottom tips |
  | `'` `` ` `` | High rounding / top tips |
  | `.-` `-.` | Upper corners |
  | `` `- `` `-'` | Lower corners |
  | `V` | Bottom point of a heart |
  | `Y` / `X` | Junctions |
- **Diagonal steepness.** A `/` occupies one cell of roughly 1:2 (width:height), so a run of `/` stepping one column per row reads as about 63°, not 45°. A true 45° line needs about two columns per row (`//`, `\\`, or `_/` / `\_` pairs). The generated heart outline in section 4 shows this doubling on its shallow parts.
- **Joins with box-drawing.** Box-drawing joins only look seamless when `line-height` equals the font's em box, typically `line-height: 1` in CSS. Larger line-heights leave gaps in verticals. Pure-ASCII `|` art tolerates any line-height.
- **Example: three button-border styles** (the third uses Unicode rounded box-drawing):
  ```
  +-------------+    .-------------.    ╭─────────────╮
  |   O P E N   |    |    OPEN     |    │    OPEN     │
  +-------------+    '-------------'    ╰─────────────╯
  ```
  A pressed or hover state can swap to a double border (`=` and `#`, or `╔═╗`) or shift the label by one cell.
- **Braille range.** Braille Patterns are U+2800–U+28FF. Each cell is a 2×4 dot grid, which gives 8 sub-pixels per character, the highest resolution of any common text-art set. This is well-established Unicode knowledge but was not re-fetched this session.
- **Heart glyph.** `♥` (U+2665) is not ASCII. A strictly 7-bit page should use `<3` or a multi-line drawn heart.

### Gaps
- No source fetched on which web fonts have the best box-drawing and braille coverage, or on browser line-height gaps. Test in the target browsers (for example a stack such as `"DejaVu Sans Mono", Consolas, "Courier New", monospace`; not verified).
- No source fetched for the Unicode version that added the octant characters.

## 2. Character density ramps, per-font calibration, gamma/contrast

### Takeaway
The two canonical ramps come from Paul Bourke (1997): a 70-character ramp ordered dense to sparse, and a 10-character ramp ordered sparse to dense, which Bourke calls "more convincing". jp2a uses its own 21-character ramp and Rec.601-style RGB weights. A ramp's apparent darkness depends on the typeface, so the most accurate ramp is measured from the actual font. Contrast and gamma are applied to the lightness before it is quantised to a ramp index.

### Cited Findings
- Bourke's standard 70-character ramp, ordered black to white (dense ink first). The source page cites it as follows:
  ```
  $@B%8&WM#*oahkbdpqwmZO0QLCJUYXzcvunxrjft/\|()1{}[]?-_+~<>i!lI;:,"^`'.
  ```
  The ramp ends with a backtick, an apostrophe and a full stop. — [Paul Bourke, "Character representation of grey scale images"](https://paulbourke.net/dataformats/asciiart/)
- Bourke's 10-level ramp, which he calls "more convincing": `" .:-=+*#%@"` (space first, so sparse to dense). — [Paul Bourke](https://paulbourke.net/dataformats/asciiart/)
- Bourke notes that different typefaces look more or less dark for the same character, so grey levels can be uneven. The page is dated February 1997 and was updated in 2002. — [Paul Bourke](https://paulbourke.net/dataformats/asciiart/)
- jp2a's default ramp is `" ...',;:clodxkO0KXNWM"`, settable with `--chars=`. Its RGB-to-grey weights default to red=0.2989, green=0.5866, blue=0.1145, settable with `--red/--green/--blue`. `--background=dark|light` tells it which way to map the ramp, and `--invert` flips it. — [jp2a man page (Debian)](https://manpages.debian.org/testing/jp2a/jp2a.1.en.html)
- ascii-image-converter takes a custom ramp via `--map` (darkest to lightest, for example `" .-=+#@"`) and has `--complex` for a wider built-in set. — [ascii-image-converter README](https://github.com/TheZoraiz/ascii-image-converter)
- Alex Harri's baseline renderer computes per-cell lightness as relative luminance from RGB and maps it through a 10-character ramp from space to `@`. — [Alex Harri, "ASCII characters are not pixels" (2026-01-17)](https://alexharri.com/blog/ascii-rendering)
- Harri's contrast enhancement normalises each cell's sampling vector by its maximum component, raises it to an exponent, then scales it back. Dark parts get darker while near-uniform cells, and so smooth gradients, are mostly preserved. — [Alex Harri](https://alexharri.com/blog/ascii-rendering)

### Inferences
- **Mind the ramp direction.** The page is presumably light text on a dark background, which is common for ASCII pages. There, bright pixels should get dense glyphs (`@`), which is the reverse of Bourke's print-oriented "dense = black". Pick one convention and reverse the string once.
- **Calibrate a ramp to the real font.** For each printable character, render it in the page's actual font (Pillow `ImageFont.truetype` + `ImageDraw.text` into a cell-sized bitmap) and count the inked pixels. Sort by coverage, drop near-duplicate densities, then normalise coverage to 0..1. To map a lightness L, pick the glyph with the nearest coverage, not an evenly spaced index. This removes Bourke's "uneven grey levels" problem.
- **Gamma.** Convert sRGB to linear light before averaging pixels within a cell. Then pick glyphs either by perceived lightness (re-apply gamma, or use CIE L*) or by linear coverage. Glyph coverage blends roughly linearly at viewing distance, so matching linear luminance to coverage is the physically motivated choice. An extra contrast exponent (as in Harri) or a histogram stretch is applied before quantising.
- **Choosing a ramp size.** Long ramps (70 characters) contain many glyphs of near-equal density with very different shapes (`b d p q`), which adds visual noise. The 10-character ramp is cleaner for textures such as paper grain or wax shading.
- **Example: gradient with the 10-character ramp,** dark to light (repeat each glyph for width):
  ```
     ...:::---===+++***###%%%@@@
  ```

### Gaps
- No published per-font calibration table (for example coverage values for Consolas or Courier) was found.
- No primary source fetched on sRGB linearisation for ASCII specifically. The gamma advice above is inference from general imaging practice.

## 3. Image-to-ASCII conversion algorithms

### Takeaway
The baseline converter works in five steps:
1. Divide the image into font-shaped cells, correcting for the roughly 2:1 cell height.
2. Average each cell's luminance.
3. Optionally stretch contrast or dither.
4. Index into a ramp.
5. Optionally colour each glyph.

Better quality comes from matching glyph *shape* rather than only brightness:
- Xu, Zhang & Wong (2010) used an alignment-insensitive shape metric with constrained deformation to make line-structure art.
- Alex Harri (2026) used per-cell "shape vectors" sampled with 6 circles, nearest-neighbour lookup and directional contrast enhancement.
- jp2a has a cheap middle ground: edge-only output with direction-dependent glyphs.

### Cited Findings
- **Aspect ratio.** Character cells are taller than wide, so images stretch vertically. The common fix is to sample half as often vertically, or to match horizontal and vertical spacing exactly when the font's aspect is known. — [Paul Bourke](https://paulbourke.net/dataformats/asciiart/)
- **Converter fidelity.** Converters reduce an image to greyscale and map brightness levels to characters. Fidelity depends on depth, sharpness and aspect ratio. AAlib and libcaca render video as ASCII. — [Wikipedia: ASCII art](https://en.wikipedia.org/wiki/ASCII_art)
- **Harri's critique of luminance ramps** (article dated 2026-01-17):
  - Treating cells as pixels ignores glyph shape and gives jagged or blurry edges.
  - Nearest-neighbour sampling aliases.
  - Supersampling smooths edges but blurs them, because each cell is still a low-resolution pixel.

  — [Alex Harri](https://alexharri.com/blog/ascii-rendering)
- **Harri's shape-based method:**
  - Each cell gets 6 staggered, slightly enlarged sampling circles. This captures left/right differences (`p` vs `q`) and the middle (`-`), which 2 circles miss.
  - Each printable glyph's "shape vector" is the fraction of each circle it covers, normalised per component by the maximum across all glyphs.
  - At runtime the image lightness in each circle forms a sampling vector, and the glyph with the minimum (squared) Euclidean distance wins.
  - Shape vectors are precomputed.

  — [Alex Harri](https://alexharri.com/blog/ascii-rendering)
- **Harri's directional contrast:**
  - Ten external circles sample just outside the cell. Each internal component is normalised using the maximum of the external values that affect it, which sharpens boundaries.
  - Global contrast alone causes "staircasing" when all samples in a cell are equally light. Widened directional enhancement fixes it.

  — [Alex Harri](https://alexharri.com/blog/ascii-rendering)
- **Harri's performance notes:**
  - Brute-force search is too slow for animation (a budget of a few thousand characters per frame at 60 FPS on a laptop).
  - He uses k-d trees for the 6-D search, plus a cache keyed by quantising each component to 5 bits. For example, 6 levels needs about 364 KB and 12 levels about 22.78 MB.
  - Sampling and contrast moved to a six-pass GPU shader pipeline.
  - Character colouring was out of scope.

  — [Alex Harri](https://alexharri.com/blog/ascii-rendering)
- **Xu, Zhang & Wong, "Structure-based ASCII Art",** *ACM Transactions on Graphics* 29(4), SIGGRAPH 2010, pp. 52:1–52:9:
  - It targets the hand-made style that traces an image's main *lines*, not its tones.
  - The core contribution is an alignment-insensitive shape similarity (AISS) metric that tolerates misalignment while still accounting for position, orientation and scale.
  - It adds constrained deformation of the input, with generation posed as minimising shape dissimilarity plus deformation.
  - Tone-based methods give "halftone-like results" and need high text resolution.
  - The project page offers the paper, slides, a user study and a gallery, but no source code.

  — [Project page (CUHK / ttwong12.github.io)](https://ttwong12.github.io/papers/asciiart/asciiart.html)
- **jp2a edge and colour options:**
  - `--edges-only` draws only edges (a line-drawing effect), using directional glyphs above `--edge-threshold` (about 0.5 is a suggested start).
  - `--html` emits HTML.
  - `--colors` uses truecolour or ANSI in text output and CSS colours in HTML. `--color-depth` takes 4, 8 or 24.
  - `--fill` colours each character's background in HTML colour mode.

  — [jp2a man page](https://manpages.debian.org/testing/jp2a/jp2a.1.en.html)
- **Chafa history:**
  - Braille symbols arrived in 1.0.0.
  - Ordered and diffusion dithering arrived in 1.2.0.
  - Sextant and legacy-wedge symbols and `--fg-only` arrived in 1.8.0.
  - The ASCII symbols were reworked, and a Latin class added, in 1.12.0.
  - Blue-noise dithering (`--dither noise` in symbols mode) arrived in 1.16.0 (2025-05-18).

  — [chafa NEWS](https://raw.githubusercontent.com/hpjansson/chafa/master/NEWS)
- **ascii-image-converter:** braille output (`--braille`) with `--threshold` (0–255) and `--dither`; colour (`--color`, `--color-bg`); `--negative`; `--save-txt` / `--save-img`; and a Go library package (`aic_package`). — [ascii-image-converter README](https://github.com/TheZoraiz/ascii-image-converter)

### Inferences
- **A practical Python pipeline for this project.** Use Pillow and NumPy only:
  1. Load the image and convert to linear luminance.
  2. Resize to `(cols, rows)` with `rows = cols * (img_h/img_w) * (cell_w/cell_h)`. `cell_w/cell_h` is about 0.5 for most monospace fonts at `line-height: 1`; measure it.
  3. Apply a contrast curve.
  4. Optionally apply Floyd–Steinberg error diffusion over the ramp levels. Diffusion matters most with short ramps, while 10+ levels often look better undithered.
  5. Index into the calibrated ramp.
  6. `html.escape()` each row, so that `<`, `>` and `&` in the ramp cannot break the markup.
- **Shape matching for clean outlines.** For the envelope and heart outlines, a cheap version of Harri works well:
  - Rasterise each candidate glyph (`/ \ | _ - ( ) . ' ` , V`) in the page font into, say, a 2×3 or 3×6 coverage grid.
  - Do the same for each cell of a high-resolution line drawing.
  - Pick the nearest glyph by L2 distance.

  Brute force over about 95 glyphs is fine for a static page generated once in Python.
- **Colour ASCII on the web.** Wrap runs of same-coloured glyphs in `<span style="color:#rrggbb">`, merging adjacent cells with equal colour to keep the HTML small. jp2a's `--html --colors` output is a working reference for the markup.

## 4. Drawing shapes into a character grid (lines, parametric curves, fills, SDFs, slope glyphs)

### Takeaway
To draw procedurally, keep a 2-D char grid in "cell space" and remember that one row is about two columns tall. Then use the right tool for each element:
- **Outlines:** sample a curve densely, or Bresenham between points, and pick the glyph from the on-screen tangent angle (`_` `/` `|` `\`).
- **Solid fills:** evaluate an inside test (implicit inequality, polygon scanline or SDF ≤ 0) at each cell centre.
- **Shading:** map SDF distance or a lighting term through a density ramp.

The heart is easiest as the implicit curve `(x²+y²−1)³ − x²y³ ≤ 0` for fills, and the parametric `x=16 sin³t, y=13 cos t − 5 cos 2t − 2 cos 3t − cos 4t` for outlines.

### Cited Findings
- MathWorld lists the parametric heart `x = 16 sin³t`, `y = 13 cos t − 5 cos 2t − 2 cos 3t − cos 4t` with no attribution. It also lists:
  - the implicit `(x² + y² − 1)³ − x²y³ = 0` (from the y=0 cross-section of the heart surface);
  - the polar `r = 1 − sin θ` (a rotated cardioid);
  - `x² + [y − (x²)^(1/3)]² = 1` (J. Schroeder, 2021).

  — [Wolfram MathWorld: Heart Curve](https://mathworld.wolfram.com/HeartCurve.html)
- Edge-aware converters choose direction-dependent glyphs where the gradient exceeds a threshold (jp2a `--edges-only` / `--edge-threshold`). This is the image-space counterpart of slope-based glyph choice. — [jp2a man page](https://manpages.debian.org/testing/jp2a/jp2a.1.en.html)
- Bourke's aspect advice also applies to procedural drawing: sample half as often vertically, or use the known font aspect. — [Paul Bourke](https://paulbourke.net/dataformats/asciiart/)

### Inferences
These come from the researcher's own code, run with Node v24 in this session (scratchpad `heart.js`), and from standard graphics knowledge.

- **Filled heart from the implicit inequality.** Grid 31×13 with x and y scaled to ±1.3; rows count double, so 13 rows ≈ 26 "column-heights":
  ```
         ######     ######
      #######################
     #########################
    ###########################
     #########################
     #########################
       #####################
         #################
           #############
              #######
                 #
  ```
  To get a textured wax seal, replace `#` with a ramp lookup on `f = (x²+y²−1)³ − x²y³` (more negative means deeper inside, so denser), or on a fake light direction.
- **Heart outline from the parametric curve**, with glyphs chosen from the tangent angle on screen. The tangent comes from the analytic derivative, `dx/dt = 48 sin²t cos t` and `dy/dt = −13 sin t + 10 sin 2t + 6 sin 3t + 4 sin 4t`, with dy scaled ×2 for the cell aspect. Angle bins: below 22.5° → `_`, 22.5–67.5° → `/`, 67.5–112.5° → `|`, otherwise `\`.
  ```
      _______\       _______\
   ////      \\\\ ////      \\\\
  //            \|/            \|
  |              |              |
  |                             /
   \\                         //
    \\\                     ///
      \\\                 ///
        \\\\           ////
           \\\       ///
             \\\   ///
               \\\//
                 \
  ```
  - **Artefacts to fix:** stray `\` at the top-right of each lobe, and the doubled `\\\\` / `////` runs, which are the 2:1 aspect effect from section 1.
  - **Fixes:**
    - Choose one glyph per cell by majority vote or by the sample nearest the cell centre, instead of "last write wins".
    - Use `.` / `'` / `` ` `` at local extrema (the lobe tops, the bottom tip `V`).
    - Hand-touch the result. Most good ASCII hearts are hand-tidied.
- **Lines (Bresenham).** Bresenham's integer line algorithm steps along the major axis, accumulating an error term to decide minor-axis steps. Pick the glyph once per segment from its screen angle with the same bins. Horizontal runs look best as `_` when the line is the lower edge of a shape and `-` when it is a mid-line.
- **Filled polygons (scanline).** For each row, intersect the polygon edges with the row's centre line `y = r + 0.5`, sort the x-crossings, and fill between pairs. The envelope body, flap triangle and letter paper are all polygons.
- **Signed distance fields (SDF).** Define each shape as `d(x,y)` (negative inside) and combine shapes with `min` (union), `max` (intersection) and `max(a, −b)` (subtraction). Then render each cell by its distance:

  | Distance | Render as |
  |---|---|
  | `d < −w` | Fill glyph or ramp |
  | `|d| < w` | Outline, glyph from the gradient direction `∇d` |
  | Otherwise | Background texture |

  SDFs make borders of constant thickness and rounded corners trivial, which suits a rounded button or a wax-seal ring.
- **Layered composition.** Keep a list of layers (background texture, envelope, flap, seal, text). Each layer is a grid in which a sentinel character (for example `~` or `None`) is transparent, and the layers are painted in order. The envelope below was generated this way (scratchpad `envelope.js`), with an assert that every row has equal width:
  ```
   ______________________________________
  |\                                    /|
  | \                                  / |
  |  \                                /  |
  |   \                              /   |
  |    \                            /    |
  |     \        .--. .--.         /     |
  |      \      (    V    )       /      |
  |       \      \       /       /       |
  |        \______`.   .'_______/        |
  |                 `.'                  |
  |                                      |
  |                                      |
  |______________________________________|
  ```
  The 11-wide seal on a 40-wide envelope ends up one cell off-centre. Use odd outer widths so sprites can centre exactly.

### Gaps
- No primary source fetched this session for Bresenham, scanline fill or SDF rendering. These are standard algorithms described from general knowledge.
- No published study of the "best" angle-to-glyph bins was found. The bins above are a working heuristic.

## 5. Big text / banners: FIGlet format, pyfiglet, fonts, licensing, alternatives

### Takeaway
FIGlet fonts (`.flf`, the FIGfont v2 spec) are the standard way to get huge ASCII headlines. In Python, use pyfiglet 1.0.4 (the latest on PyPI as of 2026-10-31, released 2025-08-15; MIT; Python ≥3.9):
- `pyfiglet.figlet_format(text, font=..., width=...)` returns a plain string.
- Raise `width` above the default 80, or a long headline like "Will you open ?" wraps.

pyfiglet ships fonts whose licences vary. Fonts with a clear redistribution licence are in `fonts-standard`; others are distributed on a public-domain assumption. toilet `.tlf` fonts (some made of Unicode blocks) are also bundled.

### Cited Findings
- **FIGfont v2 header.** Example `flf2a$ 6 5 20 15 3 0 143 229`, with fields in order:

  | Field | Example value and meaning |
  |---|---|
  | Signature | `flf2a` (the final `a` is ignored but required) |
  | Hardblank | `$`, which renders as a space but blocks smushing |
  | Height | 6 |
  | Baseline | 5 |
  | Max_Length | 20 (widest line + 2 for endmarks) |
  | Old_Layout | 15 (range −1..63) |
  | Comment_Lines | 3 |
  | Print_Direction | 0 = left-to-right, 1 = right-to-left |
  | Full_Layout | 143 (range 0..32767, a bitfield) |
  | Codetag_Count | 229 (total characters − 102) |

  The first 7 fields are required. — [FIGfont spec (figfont.txt)](https://github.com/cmatsuoka/figlet/blob/master/figfont.txt)
- **Endmarks.** Each line of a FIGcharacter ends with an endmark, usually `@` or `#`. By convention the last line has two, and the driver strips the trailing run of endmarks. — [FIGfont spec](https://github.com/cmatsuoka/figlet/blob/master/figfont.txt)
- **Layout modes:**
  - Full width: no overlap.
  - Fitting/kerning: characters move together until they touch.
  - Smushing: characters overlap by one more column.

  The six horizontal smushing rules (with their bit codes):

  | Rule | Code | Effect |
  |---|---|---|
  | Equal character | 1 | Identical sub-characters merge |
  | Underscore | 2 | `_` is replaced by a bracket, slash or pipe |
  | Hierarchy | 4 | Six classes; the later class wins |
  | Opposite pair | 8 | Opposing brackets become `\|` |
  | Big X | 16 | `/\`→`\|`, `\/`→`Y`, `><`→`X` |
  | Hardblank | 32 | Two hardblanks become one |

  — [FIGfont spec](https://github.com/cmatsuoka/figlet/blob/master/figfont.txt)
- **Font comments and copyright.** The spec says font comments "should at least include your name and Email address". Its sample comment allows modification provided the modifier's name is added on a comment line. The spec itself is "Copyright 1996, 1997 by John Cowan and Paul Burton" and "May be freely copied and distributed." — [FIGfont spec](https://github.com/cmatsuoka/figlet/blob/master/figfont.txt)
- **FIGlet itself.** The current C FIGlet is 2.2.5 (May 2012). figlet.org hosts a font database (`/cgi-bin/fontdb.cgi`) and FTP archives (standard, contributed, international and MS-DOS fonts). — [figlet.org](http://www.figlet.org/)
- **pyfiglet releases.** The latest is 1.0.4 (2025-08-15). Earlier: 1.0.3 (2025-06-02) and 1.0.2 (2023-09-13); 1.0.0 and 1.0.1 were yanked for breaking older Pythons. It requires Python ≥3.9 and is MIT-licensed. — [pyfiglet on PyPI](https://pypi.org/project/pyfiglet/)
- **pyfiglet API (source):**
  - `figlet_format(text, font=DEFAULT_FONT, **kwargs)` returns `Figlet(font, **kwargs).renderText(text)`.
  - `Figlet(font='standard', direction='auto', justify='auto', width=80)`, where direction is `auto|left-to-right|right-to-left` and justify is `auto|left|center|right`.
  - `FigletFont.getFonts()` returns a list of names, and `FigletFont.isValidFont(font)` checks a font.
  - `print_figlet(text, font, colors=":")` prints with ANSI colour.
  - Hardblanks are replaced with spaces in the output.

  — [pyfiglet/__init__.py](https://raw.githubusercontent.com/pwaller/pyfiglet/main/pyfiglet/__init__.py)
- **pyfiglet CLI (optparse):**

### Inferences
- **Minimal usage in the page generator:**
  ```python
  import html, pyfiglet
  art = pyfiglet.figlet_format("Will you open ?", font="big", width=200)  # avoid wrap at 80
  pre = f'<pre class="headline" aria-label="Will you open?">{html.escape(art)}</pre>'
  ```
  `aria-label` (or a visually hidden real heading) keeps the headline readable to screen readers, which would otherwise spell out punctuation soup.
- **Measure before shipping.** Measure the rendered width with `max(len(l) for l in art.splitlines())` and scale with CSS `font-size` (for example `clamp()` or `vw` units) so the `<pre>` fits mobile screens. Never let the browser wrap a FIGlet `<pre>`; use `white-space: pre` and `overflow-x: auto`.
- **Candidate fonts for a huge, readable headline.** These are bundled names recalled from pyfiglet's font set and were not verified this session; confirm with `pyfiglet -l` and preview each:
  - Readable outline: `standard`, `big`, `doom`, `slant`, `banner3`, `colossal`, `univers`, `roman`.
  - Solid Unicode-block look: `ansi_shadow`, `ansi_regular`, `bloody`. These are not pure ASCII.
  - Romantic script look: `script`.
- **The "?" spacing.** In "Will you open ?" the space before `?` survives FIGlet rendering, but smushing can make it look narrower. A deliberately wider gap can be forced with two spaces or a hardblank-like non-smushing character.
- **Alternatives:**
  - toilet: C, supports `.tlf` colour and Unicode fonts plus filters.
  - Hand-rolled block font: map each letter to a 5×7 bitmap and print each "pixel" as `##` or `██` (two columns per pixel, which corrects the 2:1 cell aspect).
  - asciiart.eu's "Text to ASCII Art" generator. Its navigation lists one, but it was not verified to be FIGlet-based.

### Gaps
- The current toilet version was not fetched. It is widely cited as 0.3, but this is unverified here.

## 6. Envelope / letter / heart conventions, archives, signing and reuse etiquette

### Takeaway
ASCII art archives (asciiart.eu, Joan Stark's "jgs" work from Usenet `alt.ascii-art`) follow a strong norm: art is signed with the artist's initials in a corner, and those initials must never be removed. Unsigned reposts are tagged "Unknown" or "[nosig]", and permission should be asked for repeated use; selling someone else's art is out. For a personal love-letter page, the cleanest options are to draw the envelope and heart yourself (and optionally sign them) or to reuse archive art with initials intact and permission asked.

### Cited Findings
- **asciiart.eu FAQ rules:**
  - "DO NOT remove these initials" (compared to cutting the signature off a Van Gogh).
  - Rule 1: leave initials on when reposting.
  - Rule 2: if a piece has no initials, say you did not draw it. Unsigned art has been tagged "Unknown" or "[nosig]".
  - Rule 3: an original signed version may be reposted over an unsigned copy.

  — [asciiart.eu FAQ](https://www.asciiart.eu/faq)
- **The FAQ's "Ten Commandments":**
  - "Thou shalt not remove the initials from any ASCII art."
  - "Thou shalt ask permission before using someone else's ASCII art."
  - Do not sell others' art.
  - For signature files or any repeated use, "really e-mail the artist" and ask.
  - Usenet posting does not grant reuse rights.
  - Artists generally "don't mind" non-profit reposting but object to merchandise.

  — [asciiart.eu FAQ](https://www.asciiart.eu/faq)
- The FAQ's example snow-scene piece is credited to Joan Stark and shows her "jgs" mark. — [asciiart.eu FAQ](https://www.asciiart.eu/faq)
- Joan Stark was a prolific artist on Usenet's `alt.ascii-art` in the mid-1990s, a major venue for the form. — [Wikipedia: ASCII art](https://en.wikipedia.org/wiki/ASCII_art)
- asciiart.eu's navigation lists tools including Image to ASCII Art, Text to ASCII Art, Border Maker and Pattern Maker. — [asciiart.eu FAQ page navigation](https://www.asciiart.eu/faq)
- A third-party listing describes asciiart.eu as holding over 11,000 pieces across dozens of categories, with no API. This is a secondary source and was not verified on the site. — [archivarix listing](https://echo.archivarix.net/pt/archive/asciiart-eu)
- Combinations of styles are often used as signatures, for example at the end of an email. — [Wikipedia: ASCII art](https://en.wikipedia.org/wiki/ASCII_art)

### Inferences
- **Common envelope idioms** (researcher's description, consistent with the section 4 example):
  - A top row of `_`.
  - `|` sides, with `|\` and `/|` at the top corners.
  - Diagonal flap lines `\` and `/` converging on the centre, with the flap's lower edge drawn as `\_____/`.
  - A seal or heart centred where the flap tip lands.
  - An open envelope inverts the flap, so the diagonals rise to a peak (`/\`) above the body with a letter poking out.
- **Common heart idioms:**
  - Small: `<3`; one-line glyphs such as `♥` are not ASCII.
  - Medium:
    ```
     .--. .--.
    (    V    )
     \       /
      `.   .'
        `.'
    ```
    (Researcher's own drawing.)
  - Large: filled with `#` or `@`, or a ramp-shaded generated heart (section 4).
- **Signing your own art.** Putting your own initials in the bottom-right corner (for example `  -tH` or `ah`) follows the culture and also marks the art as original.

### Gaps
- The asciiart.eu envelope category URL guessed here (`/objects/envelopes`) returned 404, and a web search did not surface a confirmed envelope/letter page. The archive's actual envelope and heart pieces, and their artists' initials, were not inspected.
- The legal copyright status of archive ASCII art was not researched; only community etiquette was. The FAQ is etiquette, not legal advice.

## 7. Tools for making / editing ASCII art

### Takeaway
- **Diagram-like line art:** ASCIIFlow (web, MIT).
- **Coloured "text-mode" pixel art with palettes and layers:** REXPaint (1.70, Windows), Playscii (9.17.1, cross-platform, Python) or Moebius (ANSI/BBS-style, Apache-2.0).
- **Converting images:** jp2a (1.3.x, has `--html` output), chafa (1.18.3, Unicode mosaics, dithering) and ascii-image-converter (braille, colour, Go).
- **Headlines:** pyfiglet 1.0.4 or FIGlet 2.2.5.

For a Python-generated page, these tools are mainly for *authoring* assets, which are then embedded as text files.

### Cited Findings
- **ASCIIFlow:** "a client-side only web based application for drawing ASCII diagrams", hosted at asciiflow.com, MIT-licensed, about 6.0k GitHub stars. No release version is published. — [ASCIIFlow GitHub](https://github.com/lewish/asciiflow)
- **REXPaint:** a "powerful and user-friendly" ASCII art editor for Windows, with `.ans` import/export and PNG export. 1.70 (build 240110, about Jan 2024) added font-bitmap autoscaling, `.gpl` (GIMP) palettes and better `.ans` support. 1.50 and 1.60 extended font support. No newer release was found. — [REXPaint itch.io](https://kyzrati.itch.io/rexpaint), [REXPaint 1.70 devlog](https://kyzrati.itch.io/rexpaint/devlog/663211/rexpaint-170-released)
- **Playscii:** the newest release found is 9.17.1 (2021-01-22), plus a 9.17.1b hotfix (May 2021) restoring Windows 7 compatibility. Development is described as slow. — [Playscii 9.17.1 devlog](https://jp.itch.io/playscii/devlog/214916/playscii-9171)
- **Moebius:** ANSI/ASCII art editor from blocktronics, Apache-2.0 licence, about 956 stars. No current version number was found. A third-party tracker says the last push was about 2 years ago (undated). A MoebiusXBIN fork adds custom-font support. — [Moebius GitHub](https://github.com/blocktronics/moebius), [glyphdrawing.club on Moebius](https://blog.glyphdrawing.club/moebius-ansi-ascii-art-editor-with-custom-font-support)
- **jp2a:** "a simple JPEG/PNG/WebP to ASCII converter". The Debian testing package is 1.3.3-2, while its man page text says version 1.3.0 (dated 2024-09-22); treat 1.3.x as current. Options:
  - `--html`, `--html-title`, `--fill`
  - `--colors`, `--color-depth`
  - `--chars`, `--invert`, `--background`
  - `--edges-only`, `--edge-threshold`
  - `--width`, `--height`

  — [jp2a GitHub](https://github.com/Talinx/jp2a), [jp2a man page](https://manpages.debian.org/testing/jp2a/jp2a.1.en.html)
- **chafa** (latest 1.18.3, 2026-09-23; 1.18.0 was 2025-11-09):
  - Converts images and animated GIFs to sixel, Kitty, iTerm2 or "Unicode mosaics".
  - Combines symbols from selectable ranges (for example `--symbols vhalf`).
  - Colour modes: truecolour, 256, 16, or fg/bg only.
  - Dithering: ordered, diffusion and noise.
  - 1.18.2 (2026-04-30) was a security-hardening release that advises sanitising CLI parameters from untrusted sources.

  — [chafa NEWS](https://raw.githubusercontent.com/hpjansson/chafa/master/NEWS), [chafa home](https://hpjansson.org/chafa/)
- **ascii-image-converter:** Go, Windows/Linux/macOS. Accepts JPEG/PNG/BMP/WEBP/TIFF/GIF; offers braille, dithering, colour and custom `--map`; saves as TXT, PNG or GIF. — [ascii-image-converter README](https://github.com/TheZoraiz/ascii-image-converter)
- **Earlier editors and libraries:** TheDraw, ACiDDraw and PabloDraw are classic ANSI editors; AAlib and libcaca are rendering libraries. — [Wikipedia: ASCII art](https://en.wikipedia.org/wiki/ASCII_art)

### Inferences
- **Which tool for which asset:**
  - **Envelope and letter outline:** hand-draw in ASCIIFlow or any monospace editor, or generate with the Python layer/scanline approach in section 4, then hand-tidy.
  - **Paper or wax textures:** generate in Python with a calibrated ramp and noise. Or convert a photo of real paper or wax with jp2a `--chars` set to your ramp and `--html --colors`, if colour is wanted.
  - **Headline:** pyfiglet at build time.
  - **Buttons:** template strings, `+---+` style or rounded box-drawing, generated to fit the label length.
- **Keep the output plain text.** chafa's strength is terminal graphics (sixel/Kitty) and Unicode mosaics. For a web page, use only its symbols output with an ASCII-only symbol class. jp2a's HTML output is more directly reusable.
- **Store assets with their source.** Keep authored assets as `.txt` files in the repo and load them in Python with `encoding="utf-8"`. Then strip trailing whitespace consistently and pad rows to equal width so they compose.
